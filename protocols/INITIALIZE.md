# Initialization and retrofit

## New project
Classify goal, stack, deployment, auth/persistence, constraints and non-goals. Search related project aliases and accessible repos before creating; preserve existing project if continuation. Choose established conventions. For suitable web apps use Next.js/Vercel/Supabase when appropriate; never impose it on native/game/local work. Proactively provide https://vercel.com/templates/next.js/supabase and the best recommended account. If a direct deploy link is verified include it; do not invent links. Give https://github.com/new when needed and copyable repo name, description, visibility, initialization options. Identify manual OAuth/account selection only if needed. For ambiguous account writes or paid resources seek required approval. Prevent duplicates with a final existence check before creating.
After user-created starter, verify GitHub owner/repo and baseline SHA, Vercel Git link and deployment, Supabase project ref and connectivity, environment variable names/scopes without values, auth and build/test separately. Same name does not verify integration.
Preserve starter baseline SHA or approved branch/tag. Use established branch workflow; new repo defaults main stable and develop/task branch, subject to deploy configuration and protection. Empty docs repo initial main setup permitted when explicitly requested. No unintended upstream edits.
Clean demo content only after checking needed auth/build/config/integration. Preserve lockfile, migrations, tests, license and config. Re-run checks. Initialize knowledge roles from WISDOM using real context, not filler.

## Retrofit
Inspect tree, framework, nested AGENTS, existing docs and history. Map knowledge roles to existing paths. Reuse equivalents rather than duplicate; do not rename just for convention. If AGENTS missing, read README, docs and code; report during audit, create during authorized implementation. Determine active/obsolete plans using evidence, preserve uncertain historical records, never mark past functionality verified without evidence.
Significant directory = human-maintained module/service/package, documentation, tests, migration, shared assets, tooling or distinct rules. Exclude dependencies/vendor, generated output, caches, .git and trivial leaves. Create NAVIGATION.md describing purpose, entrypoints, dependencies, scoped rules, tests and links. For small modules parent map may suffice. Update when moved. Verify fresh-agent traversal and links.
